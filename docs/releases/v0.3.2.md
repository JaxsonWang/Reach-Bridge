# Reach-Bridge v0.3.2

修复浏览器待机期间重复初始化 HTTP 客户端带来的 CPU 开销，保留既有查询、登录、会话保存与回收行为。

## CPU 修复

- 镜像内的 Agent-Reach 1.6.1 带有构建期补丁：CDP `_json()` 惰性复用进程内客户端，不再为每个本机 HTTP 请求重复创建 HTTPS 上下文、加载默认 CA。
- 只缓存客户端，不缓存响应；每次仍发起请求并解析最新 JSON。禁用代理、原超时以及请求／解析失败语义不变。
- watcher 仍每约 2 秒检查活动并保存会话，空闲回收仍为 600 秒。没有靠降频或缩短保留时间降低读数。
- 健康检查改用独立的 `reach-bridge-healthcheck`，以 `http.client` 请求本机 `/readyz`，不加载 FastAPI 或默认 CA。探测间隔仍为 10 秒，请求超时 3 秒，Docker 超时 5 秒、重试 6 次、启动宽限 10 秒均不变。
- 内存策略保持不变，没有清理宿主缓存或添加内存限制。

## 依据与验证

NAS 本机 Python 3.12.16 的隔离 profiling 中，20 次原客户端构造消耗约 1.216 秒 CPU，其中默认 CA 加载累计约 1.143 秒；这些是同一调用链的包含关系，不能相加。该实验不请求平台网站，也不修改现有 watcher。

双架构 CI 使用实际安装并打补丁的上游模块，每组发送 30 个本机 HTTP 请求，对比每次构造与进程内复用：默认 CA 加载从 30 次降到 1 次，并检查客户端 CPU 成本下降。另验证新鲜响应、并发请求隔离、代理禁用、重定向、HTTP 错误、无效 JSON、超时、连接失败和构造失败。

真实浏览器 CI 保留标准 sandbox / NAS 兼容模式下的扩展、1280×800 画布及交互验收，并采样 watcher CPU、确认周期会话文件继续更新。基准中客户端 CPU 的降幅不等同于 NAS 整个容器的 CPU 降幅，后者在更新后按实际使用验证。

## 更新 NAS

镜像：`ghcr.io/jaxsonwang/reach-bridge:0.3.2-agent-reach-1.6.1`，支持 `linux/amd64` 与 `linux/arm64`。

修改现有 reach-bridge 服务镜像，拉取并重新创建该服务；保留环境变量、非 root UID/GID、卷、端口和安全选项。更新会中断该服务当前任务，管理界面需重新登录；已有平台凭据和专用浏览器资料保留。无需重新安装渠道依赖。

已有 Compose 如果写了旧的 Python `urllib.request` 健康检查，替换为：

```yaml
healthcheck:
  test: ["CMD", "reach-bridge-healthcheck"]
  interval: 10s
  timeout: 5s
  retries: 6
  start_period: 10s
```

没有覆盖 `healthcheck` 的部署直接使用镜像内置检查。随后仅更新 reach-bridge，不重启其他服务：

```sh
docker compose pull reach-bridge
docker compose up -d --no-deps reach-bridge
```

固定版本补丁随镜像提供，单独安装桥接 wheel 不会修改外部上游。补丁只针对 Agent-Reach 1.6.1，安装版本和源码匹配失败会中止构建，其他上游版本保持原包。
