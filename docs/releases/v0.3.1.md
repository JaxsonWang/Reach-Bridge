# Reach-Bridge v0.3.1

减少默认部署的空闲常驻进程：官方 Chromium 仅在网页登录需要可见画面时启动 Xvfb，空闲服务及无头浏览器不再依赖常驻显示服务。

- 默认容器入口直接交接给服务，不保留额外 Python 监督进程。
- 使用 Xvfb 原生 `-displayfd` 选择显示编号并报告就绪，不再依赖默认部署的 `xdpyinfo` 启动探测。
- 按需 Xvfb 通过 Linux 父死亡信号绑定真实 Chromium PID；保留上游 CDP pipe、正常关闭及强制回收语义，浏览器退出后释放显示服务。
- 旧官方 `/usr/bin/chromium` 选择在容器启动时迁移到内置统一入口，手动 CLI 和 WebUI 无需先重新准备；已有自定义浏览器继续保留可执行文件选择与原共享显示环境。
- 修复自定义显示环境中单次 `xdpyinfo` 超时提前终止入口的问题，仍使用既有 10 秒就绪期限。
- 保留原生模式、sandbox/NAS 兼容模式、600 秒浏览器空闲回收及既有登录时限。
- 包含自上一正式版以来新增的 B 站原生二维码登录：不启动浏览器，手机确认后验证并保存原生凭据。

## NAS 更新

镜像：`ghcr.io/jaxsonwang/reach-bridge:0.3.1-agent-reach-1.6.1`，支持 `linux/amd64` 与 `linux/arm64`。

在现有 NAS 项目中，仅将 reach-bridge 服务的镜像改为上面的固定版本，拉取并重新创建该服务。保留 `.env`、非 root UID/GID、端口、卷、安全选项及完整 `data/home`；无需更新 Agent-Reach 或重新安装渠道工具。更新会短暂中断该服务和正在执行的任务，重启后需重新登录管理界面，已保存的平台凭据保留。

使用仓库 Compose 时，更新发布包后设置 `REACH_BRIDGE_VERSION=0.3.1`（如已配置），执行：

```sh
docker compose --env-file .env --env-file upstream.env pull reach-bridge
docker compose --env-file .env --env-file upstream.env up -d --no-build --wait reach-bridge
```

更新后在无查询、无网页登录时查看 `docker top <容器名> -eo pid,ppid,comm,rss,pcpu`。使用官方 Chromium 的默认部署不再有常驻 Xvfb 和入口监督 Python；已有自定义浏览器是保留原显示环境的例外。

## 如何看待内存数字

本次 NAS 现场 cgroup v1 样本的匿名 RSS 约 63.6 MiB，文件缓存约 875.5 MiB，其中活跃文件缓存约 621.6 MiB；总用量减非活跃文件缓存约 685.3 MiB，与 Docker 约 684 MiB 的显示接近。`/dev/shm` 实际使用为 0，采样时没有 Chromium/Node。

高显示值的主要来源是文件缓存，不是已确认的 Python 内存泄漏。按需显示消除不必要的常驻进程，但不承诺 Docker 显示值按进程 RSS 等量下降；不会清理宿主缓存或改变统计口径。

## 验证

本地回归与格式检查，以及双架构真实容器 CI 覆盖：默认空闲无 Xvfb、原生模式、无头准备、标准与 NAS 兼容模式的扩展及 1280×800 登录画布、点击/输入/按键/滚动/刷新、正常关闭、CDP pipe 关闭、强杀 Chromium 后 Xvfb 释放及重新打开。真实平台的账号登录和搜索仍在使用这些能力的部署上验收。
